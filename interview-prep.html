2-Minute Pitch

I built an end-to-end ML pipeline for French property price estimation. Starting with DVF data—3.8 million government transactions—I apply 6 filtering rules to get 997,000 clean records, about 26% of the original. The core innovation is a 3-component ML model: LightGBM for spatial patterns, linear regression for the -5.38% annual trend, and hierarchical Bayesian smoothing that borrows strength from parent zones when local data is sparse. For a commune with only 10 transactions, the smoothing weight is 0.2, so 80% of the estimate comes from the department average. This produces reliable estimates even for the 40% of communes with fewer than 10 transactions. The output is 674,000 zones across 6 geographic levels, exported as GeoJSON and visualized with Mapbox GL JS using zoom-based layer switching. The whole pipeline runs in Docker with PostgreSQL/PostGIS for spatial queries.

Project Overview - Interview Q&A

Q: Tell me about this project.
I built an ML pipeline that processes French property transactions to produce price estimates at multiple geographic levels. Starting with 3.8 million government records, I filter to 997,000 quality transactions, train a spatial ML model, and generate estimates for 674,000 zones—from country level down to individual building parcels. The output is an interactive choropleth map where users can explore prices at any zoom level.
Q: What was the biggest technical challenge?
Handling sparse data at granular levels. 40% of communes have fewer than 10 transactions, and most parcels have just 1-2. A single transaction isn't statistically reliable. I solved this with hierarchical Bayesian smoothing—zones with few transactions borrow strength from their parent level. The smoothing weight is n/50, so a parcel with 1 transaction gets 98% of its estimate from the postcode average.
Q: Why 26% retention rate? Isn't that low?
Actually, 26% is appropriate for this use case. The raw DVF data includes commercial properties, land-only sales, donations, and records with missing coordinates. I only keep residential sales (houses and apartments) with valid prices, surfaces, and geocoding. The 997,000 remaining records are high-quality and representative of the actual residential market.
Q: What would you do differently?
Three things: First, I'd add ClickHouse for faster analytical queries on historical data. Second, I'd implement incremental updates instead of full reprocessing—currently the pipeline rebuilds everything when new DVF data is released. Third, I'd add more features to the ML model like proximity to metro stations, schools, and green spaces.
Q: How would you scale this to all of Europe?
The architecture scales horizontally. Each country's data would be processed independently in parallel. The main challenges would be: different data formats per country, varying data quality, and harmonizing geographic hierarchies. I'd use Airflow to orchestrate country-specific DAGs and a shared PostGIS instance with country partitioning.
Tip: Always mention specific numbers (3.8M, 997K, R²=0.517) - it shows you know your project deeply.

Architecture - Interview Q&A

Q: Walk me through your architecture.
It's a 4-layer architecture:

Infrastructure: Docker Compose orchestrating PostgreSQL, ETL, and web app containers.
Data: PostGIS for spatial storage with GIST indexes, GeoJSON for export.
Processing: Python ETL pipeline, LightGBM model, GeoPandas for spatial operations.
Presentation: Mapbox GL JS for rendering, FastAPI for the backend API.
Q: Why PostgreSQL with PostGIS instead of MongoDB or a specialized geo database?
PostGIS gives me the best of both worlds—relational integrity for transaction data plus mature spatial functions. I need ST_Within for spatial joins, ST_Distance for nearest-neighbor queries, and GIST indexes that make these 10,000x faster. MongoDB's geospatial is more limited, and specialized databases like Tile38 are overkill for batch processing.
Q: How do your Docker containers communicate?
Through a Docker network called property_network. The ETL container connects to PostgreSQL using the service name 'postgres' as the hostname—Docker's internal DNS resolves it. The web app also connects to PostgreSQL the same way. Port 5432 is exposed to the host for development access.
Q: What's the GIST index and why is it important?
GIST stands for Generalized Search Tree. It organizes spatial objects in an R-tree structure by bounding box. When I query "which commune contains this point?", without an index I'd check all 31,000 communes—31 billion checks for 1 million transactions. With GIST, I traverse the tree and only check ~3 candidates per point. That's 10,000x faster.
Q: How do you handle database credentials?
Environment variables in a .env file, loaded by Docker Compose. The .env is in .gitignore so credentials never hit the repo. The ETL container receives DATABASE_URL as an environment variable constructed from the individual POSTGRES_USER and POSTGRES_PASSWORD values.
Watch out: If asked about "microservices vs monolith" - this is a modular monolith in containers, not true microservices. Be honest about it.

ETL Pipeline - Interview Q&A

Q: Walk me through your ETL pipeline.
Extract: Download DVF CSVs from data.gouv.fr and cadastre GeoJSON from cadastre.data.gouv.fr.
Transform: Apply 6 filtering rules (sales only, residential, valid price/surface/coordinates, outlier removal), calculate price per m², format postcodes.
Load: Batch insert to PostgreSQL with 50,000 row chunks, create spatial geometries, build GIST indexes.
Q: What are your 6 filtering rules?
1. Sales only (nature_mutation = 'Vente') - removes donations, exchanges
2. Residential (type_local IN ('Maison', 'Appartement')) - removes commercial, industrial
3. Has valid price (valeur_fonciere > 0)
4. Has valid surface (surface_reelle_bati > 0)
5. Has coordinates (latitude/longitude not null)
6. Remove outliers (€100-50,000/m², 9-500m² surface)
Q: How did you choose those outlier thresholds?
Based on domain knowledge and data exploration. €100/m² is below construction cost anywhere in France—indicates data error. €50,000/m² exceeds even the most expensive Paris addresses—also likely errors. For surface, 9m² is the legal minimum for a habitable room in France, and 500m² covers 99.9% of legitimate residential properties.
Q: Why batch inserts of 50,000 rows?
Balance between memory usage and database round-trips. Smaller batches mean more network overhead. Larger batches risk memory issues—each row with geometry is about 1KB, so 50,000 rows is ~50MB in memory. I tested 10K, 50K, and 100K; 50K gave the best throughput without memory pressure.
Q: How do you handle the 22GB cadastre data?
Department by department. I never load the full 22GB. For each of 96 departments, I load its cadastre file (100-500MB), build a spatial index, match transactions to buildings, export the parcel GeoJSON, then free the memory before moving to the next department. Peak memory stays under 2GB.
Q: What's your cadastre matching rate?
About 15% overall. Higher in dense urban areas (25% in Paris) because geocoding is better and buildings are more consistently mapped. Lower in rural areas (8%) where cadastre data is sparser and transactions often geocode to town centroids rather than actual buildings. Unmatched transactions get estimated square footprints based on their surface area.

ML Model - Interview Q&A

Q: Explain your ML model architecture.
Three components:

1. Spatial (LightGBM): Predicts base price from location, property type, surface. R²=0.517.
2. Temporal (Linear Regression): Captures -5.38% annual trend, adjusts predictions to target date.
3. Hierarchical Smoothing: Combines local estimate with parent level based on sample size. Weight = n/50.
Q: Why LightGBM over XGBoost or Random Forest?
Three reasons: First, LightGBM handles categorical features natively—I don't need to one-hot encode department codes or property types. Second, it's faster for my data size (1M rows) due to histogram-based splitting. Third, leaf-wise growth often captures spatial patterns better than level-wise. In my tests, LightGBM was 3x faster than XGBoost with similar accuracy.
Q: Walk me through the smoothing formula.
weight = min(1.0, n / 50)
smoothed = weight × local + (1 - weight) × parent
Example: A commune with 10 transactions at €2,000/m², parent department at €1,500/m²:
weight = 10/50 = 0.2
smoothed = 0.2 × €2,000 + 0.8 × €1,500 = €1,600/m²

The local estimate is pulled toward the more reliable parent estimate.
Q: Why n/50 specifically?
50 transactions is roughly where estimates stabilize statistically. With 50+ sales, the local median has a narrow enough confidence interval to trust. Below 50, variance is high. I tested thresholds from 20 to 100; 50 gave the best balance between local specificity and stability in cross-validation.
Q: What's R² of 0.517 mean in practice?
The model explains 52% of price variance from location and property characteristics alone. The remaining 48% is property-specific factors I don't have: renovation state, floor level, view, amenities. For aggregated zone estimates (not individual predictions), 0.517 is quite good—the aggregation further reduces noise.
Q: How do you calculate confidence scores?
Three components, 0-100 scale:
Volume (0-40): More transactions = higher confidence. 20+ gets max points.
Precision (0-30): Narrower confidence interval relative to price = higher score.
Recency (0-30): More recent transactions = higher confidence. Decays over 30 months.

Aggregation - Interview Q&A

Q: Explain your aggregation strategy.
I aggregate 997K transactions into 6 geographic levels: country (1), region (13), department (96), commune (31K), postcode (5.7K), and parcel (643K). Each level uses spatial joins to find which transactions belong to which zone, calculates statistics, and applies hierarchical smoothing from the parent level. Total output is 674,602 zones.
Q: How do spatial joins work?
Spatial joins answer "which points are inside which polygons" using PostGIS ST_Within. The GIST spatial index is critical—it organizes zones in an R-tree by bounding box. Without the index: 31 billion comparisons, 250 days. With index: 3 million comparisons, 5 minutes. That's 10,000x faster.
Q: Why split parcels into 93 files?
642K parcel polygons would be 208 MB in one file—too large to load at once in a browser. By splitting into department files averaging 2-3 MB each (max 9 MB for Paris), the frontend can lazy load only what's visible in the viewport. User views Paris? Load just 75.json. Pan to Lyon? Unload Paris, load 69.json. Memory stays bounded.
Q: What's the largest output file?
The Paris parcel file (75.json) at 9.1 MB with about 45,000 building polygons. Paris has the highest transaction density and complex building geometries. The commune file is also large at 22 MB for 31,059 municipal boundaries. Total output is 250 MB across all levels.
Q: How do you ensure consistency across levels?
Transaction counts must sum up the hierarchy. I verify that country = sum of regions = sum of departments. Prices should be within reasonable ranges—no child zone significantly higher/lower than parent without justification. I run validation queries after each ETL run.

Frontend - Interview Q&A

Q: Why Mapbox GL JS?
Four reasons: WebGL-based for hardware-accelerated rendering of 600K+ polygons. Vector tiles for smooth zooming without pixelation. Data-driven styling expressions for choropleth colors directly from price data. Native GeoJSON support matching my export format. I considered Leaflet but it struggles with many polygons.
Q: How does zoom-based layer switching work?
Each layer has minzoom and maxzoom properties. Country shows at zoom 0-4, regions at 5-6, departments at 7-8, communes at 9-11, postcodes at 12-13, parcels at 14+. Mapbox automatically shows/hides layers based on current zoom. Only one level is visible at a time, keeping the map readable and performant.
Q: Explain your lazy loading implementation.
When zoom reaches 14+, I determine which departments are visible by checking bounding box intersections with the viewport. I fetch only those department parcel files and add them as map sources. When the user pans away, I unload departments no longer visible. I cap at 3 loaded departments to bound memory. Viewing Paris loads 9 MB instead of 208 MB.
Q: How did you design the color scale?
Diverging blue-white-red scheme. Blue for cheap (cool markets), red for expensive (hot markets), white at the €3,000 midpoint near the national median. Breakpoints based on actual distribution: €1,000 for rural, €10,000+ for Paris. I also adjust opacity based on confidence—high confidence zones are more opaque.
Q: Why no React or Vue?
For this project, vanilla JavaScript is sufficient. The codebase is small (~500 lines), Mapbox handles most interactivity, and no framework means smaller bundle and simpler deployment to GitHub Pages. If I were adding user accounts, saved searches, or complex state management, I'd consider React.
Q: Why GitHub Pages?
Free hosting, automatic HTTPS, global CDN, and push-to-deploy workflow. The 1 GB limit is plenty for 250 MB of GeoJSON. No server needed since all data is pre-computed. For a personal project demonstrating frontend skills, it's perfect.
